# Team Chat 2A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The team talks inside LUME: channels they belong to, direct messages and a thread on every lead, live (typing,
online, ticks, unread), with replies, reactions, edit and delete, photos and files, on the Chat screen and in a lead's
Team tab.

**Architecture:** Postgres tables under row-level security (a member of the conversation, or for a lead thread whoever
can see the lead); sends are plain POSTs; every change is one `pg_notify('lume_chat', …)` fanned out by the existing
notifications hub to the open streams allowed to hear it (membership cached in memory, lead visibility checked as the
stream already does for WhatsApp). Typing and presence are NOTIFY and memory only, never a table. The web screens are
built from the approved canvas boards.

**Tech Stack:** Fastify + drizzle/pg (apps/api), Postgres migrations (packages/db), shared rules (packages/core,
browser-safe via `@lume/core/shared`), Next.js + React (apps/web), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-24-team-chat-design.md` (owner rulings 2026-11-24 included). Canvas:
https://claude.ai/artifact/KTQD9PJUGQJy1U4ynACEro v6, APPROVED 2026-11-24 ("the chat window looks perfect go ahead").

## Global Constraints

- Copy speaks as LUME, never "we"; no em dashes; never a guessed pronoun (a person is named or "you").
- No outside chat service and no outside fetches (no link previews); lead data never leaves the client's server.
- Scale bar: 1,000 people, 200 streams, a channel at 5 messages a second; p95 send→seen < 300 ms (scale suite).
- People see only the channels they are members of: never listed, searched, counted or streamed otherwise.
- A lead thread, and anything from it, reaches only people who can see that lead (`leads.view` on its owner).
- Messages: 1 to 4,000 characters after trimming (a message with only a file may have no words); at most 10 files.
- Sounds only on achievements: no sound on a message.
- Every new screen from the canvas boards, both themes (Porcelain, Obsidian), never overflows (long names and words,
  huge counts shown as 99+, phone width 390 px).
- Every change follows `docs/QUALITY_PROCESS.md`: edge-case sheet, tests first, a mutation check on every guard, the
  full gate, a fresh review, then push.

## Review Focus

1. Someone taken out of a channel, or a lead moved to an owner they can't see, with a stream open: the next event of
   that conversation never reaches them, and its messages stop loading at once (Task 6 and Task 3 tests).
2. A send retried over a bad connection (the same `clientId` twice, or two at once): one message, and both answers are
   that message (Task 4 test, the held-transaction race like the WhatsApp send fix).
3. A message deleted while others have it on screen: its words are never served again (the API answers `body: null`),
   a reaction or a reply to it is refused, and their screens show "This message was deleted" live (Task 4, Task 7).
4. A 4,000-character message, a 300-character word with no spaces, emoji-only, Arabic or Urdu text, on a 390 px phone:
   the bubble wraps inside the column and nothing runs off screen (Task 7, a Playwright check at 390 px and 1366 px).
5. Unread: your own messages are never unread; a muted channel's count isn't in the Chat total; reading on one device
   clears the count on every device; a folded list's sum equals its rows' counts, 99+ past 99 (Task 2, Task 3, Task 7).

**Interfaces:**
- Produces tables: `chat_conversations(id uuid pk, kind text 'channel'|'direct'|'lead', name citext null, topic text null
  ≤ 250, lead_id uuid null unique → leads on delete cascade, direct_key text null unique, created_by uuid null,
  created_at, archived_at null, last_message_id bigint null, last_at timestamptz null)`;
  `chat_members(conversation_id, user_id, via 'person'|'group', muted bool false, last_read_id bigint 0,
  last_delivered_id bigint 0, joined_at; pk (conversation_id, user_id))`;
  `chat_messages(id bigserial pk, conversation_id, author_id uuid null (null: LUME), kind 'text'|'system', body text
  null, reply_to bigint null, client_id uuid null, edited_at null, deleted_at null, created_at;
  unique (conversation_id, author_id, client_id))`; `chat_message_edits(message_id, body, edited_at)`;
  `chat_reactions(message_id, user_id, emoji; pk all three)`; `chat_files(id uuid pk, uploader_id, message_id bigint
  null, sha256 → whatsapp_files(sha256), name ≤ 120, mime, kind 'image'|'video'|'audio'|'document', size, created_at)`;
  `chat_channel_groups(channel_id, kind 'everyone'|'team'|'role', team_id null, role_id null)`;
  `chat_list_folds(user_id, list 'channels'|'direct'|'leads', folded bool; pk (user_id, list))`.
- Produces SQL functions: `lume_chat_sees(conv uuid) RETURNS boolean` (member, or lead thread whose lead the person can
  see) and `lume_chat_sync_groups() RETURNS void` (group members in and out, active users only).
- Produces permissions: `chat.use` (Chat, unscoped), `chat.channels.manage` (Chat, unscoped).

Decisions the implementer can't make alone:
- Channel names: `^[a-z0-9][a-z0-9-]{0,79}$`, unique among channels not archived. Direct messages: 2 to 8 people,
  `direct_key` = the member ids sorted and joined with `,` (one conversation per set of people).
- Row security (forced) on every chat table: conversations and messages, files, reactions and edits through
  `lume_chat_sees`; `chat_members` rows of conversations the person sees; `chat_list_folds` only one's own. The backup
  role reads all, like every table (`backup_read`). The worker role gets nothing.
- `lume_chat_sync_groups` runs from statement-level triggers on `user_roles`, `team_members`, `users` (status) and
  `chat_channel_groups`; it adds `via = 'group'` members for active users matched by a channel's groups and removes
  `via = 'group'` members no longer matched (a `via = 'person'` member stays).
- The migration grants `chat.use` to every existing role, `chat.channels.manage` to every role holding `roles.manage`,
  and makes #general (group: everyone) and #wins (group: everyone) if no channel has those names. defaults.ts: every
  preset gets `chat.use`; Admin gets `chat.channels.manage`.
- Audit words: `chat.channel.created`, `chat.channel.changed`, `chat.channel.archived`, `chat.members.changed`,
  `chat.message.edited`, `chat.message.deleted` (area "Chat").

- [ ] **Step 1: Write the failing tests** in `packages/db/src/chat.test.ts`:
  `"a person reads only the channels they are in"` (two users, one channel with one of them: the other's

  `"a lead thread follows the lead: who can see the lead reads it, and stops when the lead moves away"`;
  `"a team on a channel keeps its people in: joining the team adds them, leaving takes them out, someone added by
  hand stays"`; `"a disabled person is taken out of group channels"`;
  `"the same clientId from the same person in one conversation is one message"` (second insert raises 23505);
  `"#general and #wins are made once, with everyone in"`. Catalog test: both keys exist; defaults: every preset has
  `chat.use`, only Admin has `chat.channels.manage`.
- [ ] **Step 2: Run them to see them fail:** `npx vitest run packages/db/src/chat.test.ts packages/core/src/rbac`
  (from the repo root, on the box). Expected: FAIL (no such table / key).
- [ ] **Step 3: Write the migration, the drizzle schema, the catalog, defaults and audit words.**
- [ ] **Step 4: Run the tests to see them pass**, plus `apps/api/test/matrix.test.ts` (no route yet, nothing changes).

Edge cases: roles (no `chat.use`: nothing readable), RLS (forced, every table), concurrency (two syncs at once: the

### Task 3: Conversations API

**Files:**
- Create: `apps/api/src/modules/chat/conversations.ts`, `apps/api/src/modules/chat/routes.ts`,
  `apps/api/src/modules/chat/conversations.test.ts`; register in `apps/api/src/app.ts`; probes in `apps/api/test/probes.ts`

**Interfaces:**
- Consumes: Task 1 tables and `lume_chat_sees`; Task 2 `channelNameProblem`, `CHAT_LIMITS`.
- Produces routes (all need `chat.use` unless said):
  - `GET /api/v1/chat` → `{ channels: ConvRow[], direct: ConvRow[], leads: ConvRow[], folds: { channels: boolean,
    direct: boolean, leads: boolean }, unread: number }`; `ConvRow = { id, kind, name, unread, muted, lastAt,
    people?: PersonLite[] (direct), lead?: { id, name, stage } }`; one query for every unread count
    (`count(*) FILTER (WHERE m.id > cm.last_read_id AND m.author_id IS DISTINCT FROM me AND m.deleted_at IS NULL)`),
    `unread` the total over conversations not muted. Lead threads listed: those with a message the person can see,
    newest first, at most 50.
  - `POST /api/v1/chat/channels` (`chat.channels.manage`) `{ name, topic?, people?: uuid[], groups?: {kind, id?}[] }`.
  - `PATCH /api/v1/chat/channels/:id` (`chat.channels.manage`) `{ name?, topic?, archived?: boolean }`.
  - `PUT /api/v1/chat/channels/:id/members` (`chat.channels.manage`) `{ people: uuid[], groups: {kind, id?}[] }`
    (the whole set; via-person members follow `people`, groups follow `groups`, then the sync runs).
  - `POST /api/v1/chat/direct` `{ people: uuid[] }` (1 to 7 others, active, not oneself) → the conversation (an existing
    one for the same set).
  - `POST /api/v1/chat/leads/:leadId` → the lead's thread, made on first use; 404 when the person can't see the lead.
  - `PUT /api/v1/chat/:id/mute` `{ muted }`; `PUT /api/v1/chat/folds` `{ list, folded }`.
- Every change of membership or name: `pg_notify('lume_chat', {c, e:'members'|'changed'})` after commit, audited.

  `"lists only the channels the person is in, their direct messages, and lead threads of leads they can see"`;

  `"a person without chat.channels.manage can't make, rename or fill a channel"` (403);

### Task 4: Messages API

**Files:**
- Create: `apps/api/src/modules/chat/messages.ts`, `apps/api/src/modules/chat/messages.test.ts`; routes in Task 3's file

**Interfaces:**
- Consumes: Task 1, Task 2 (`bodyOf`, `CHAT_LIMITS`), Task 3's conversation access.
- Produces: `MessageView = { id: number, conversationId, authorId: string | null, kind, body: string | null,
  replyTo: { id, authorId, body: string | null } | null, files: FileView[], reactions: { emoji, count, mine }[],
  editedAt: string | null, deletedAt: string | null, createdAt }`; routes:
  - `GET /api/v1/chat/:id/messages?before=<id>&after=<id>` → `{ messages: MessageView[], members: { userId,
    lastReadId, lastDeliveredId }[] }`, 50 a page, newest page first, oldest first within it.
  - `POST /api/v1/chat/:id/messages` `{ clientId: uuid, body?: string, replyTo?: number, files?: uuid[] }` → 201
    `MessageView`; the same `clientId` again → 200 with the first (`pgCodeOf(e) === "23505"` then read it back).
  - `PATCH /api/v1/chat/messages/:mid` `{ body }` (the author only; the old body kept in `chat_message_edits`).
  - `DELETE /api/v1/chat/messages/:mid` (the author only; body and files cleared from answers, kept for audit).
  - `PUT /api/v1/chat/messages/:mid/reactions/:emoji` and `DELETE` the same (one emoji grapheme, ≤ 32 bytes).
  - `PUT /api/v1/chat/:id/read` `{ upTo: number }` and `PUT /api/v1/chat/:id/delivered` `{ upTo }` (never backwards).
- Each change NOTIFYs `{c, e:'message'|'edited'|'deleted'|'reaction'|'read', m?, u?}` after commit (ids only; the
  stream reads the rest as each person).

- [ ] **Step 1: Write the failing tests**, including Review Focus 2 and 3:
  `"a send lands once and comes back in order; the conversation's last message moves"`;
  `"the same clientId twice, and twice at once, is one message, and both answers are it"` (use `apps/api/test/held.ts`);
  `"4,000 characters go, 4,001 don't; only spaces doesn't; a file alone does"`;
  `"a reply to a message in another conversation, or to a deleted one, is refused"`;
  `"only the author edits or deletes; an edit keeps the old words for the audit"`;
  `"a deleted message answers with no words and no files, and takes no reaction"`;
  `"read never goes backwards, and own messages never count as unread"`;
  `"someone who isn't a member can't read, send or react"` (404, not 403: a channel's existence isn't told).
- [ ] **Step 2 to 5:** run and fail, implement, run and pass, mutation checks, commit.

Edge cases: concurrency (edit and delete at once: the delete wins; two reactions at once: one row), data (emoji with
skin tones and ZWJ sequences; RTL text; a body of only a newline), outside world (n/a), licence (every tier).
