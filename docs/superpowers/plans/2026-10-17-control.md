# Control each client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner sets, per client, a number of places and which modules are in their plan; the licence server
signs it into the check-in answer for LUMEs that can keep it; each LUME refuses invites and restores past its
places, keeps out-of-plan modules off, and says so plainly — never removing anyone or anything.

**Architecture:** `@lume/core` gains the plan claim (`places`, four module booleans) and `ACCEPTS` gains `"plan"`;
health gains optional `modulesOn`. The licence server stores `licences.places`/`modules` (migration 0007), signs
`plan` only for installs that accept it, and serves a Plan limits card. LUME's keeper keeps the plan in its view;
invites/restores check places; module switches check the plan; when a plan arrives that excludes a module that is
on, LUME switches it off once, audits it, and notifies admins.

**Tech Stack:** TypeScript, zod, Postgres, Next.js (panel and web), Fastify, vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-17-control-design.md` · Canvas page "3 · Control each client".

## Global Constraints

- Nothing is ever removed: no person paused, no lead, no setting deleted; Calendly's connection kept.
- An install without `accepts: ["plan"]` gets no `plan` key; no `plan` in a LUME's answer = no limits.
- Places 1–10000 or null; module keys exactly `googleSheets`, `webhooks`, `googleCalendar`, `calendly`.
- Taken places = users active or suspended + invites neither accepted nor revoked nor expired.
- Words as LUME; the look of each app as it is; no violet; no vendor prefixes in apps/web CSS.

## Review Focus

1. **A plan arrives that excludes a module that's on** → switched off exactly once (not at every check), one audit
   row, one notification to admins; switching it back on refused while excluded (Task 4).
2. **Places shrink below the people using LUME** → nobody paused or removed; invites and restores refused; the line
   in People says so (Task 4, 5).
3. **Concurrent invites at the last place** → at most `places` taken (the count and insert in one transaction with a
   lock) (Task 4).
4. **Licence server older than the LUME** (refuses `modulesOn`/`accepts: plan`) → the keeper's plain-body retry keeps
   the licence; no plan = no limits (Task 4).
5. **Calendly excluded** → its bookings are acknowledged and ignored (no retries storm), its card says so, Connect
   refused (Task 4, 5).

### Task 1: core — the plan claim
`packages/core/src/licence/fleet.ts`: `PLAN_MODULES` tuple; `planClaimSchema` (strict) `{ places: int 1–10000 |
null, modules: { googleSheets, webhooks, googleCalendar, calendly: boolean } }`; `ACCEPTS` = `["announcements",
"plan"]`; `fleetHealthSchema` gains optional `modulesOn: PLAN_MODULES[]`. `state.ts`: payload `plan` optional;
`LicenceView.plan: PlanClaim | null`. Tests: payload with plan verifies, unknown module refused; view carries plan
or null.

### Task 2: licence server — storage, signing, the API
Migration `0007_plan.sql`: `licences.places int CHECK 1–10000`, `licences.modules jsonb NOT NULL DEFAULT '{}'`.
`check.ts`: sign `plan` when `accepts` includes it (`modules` filled true for missing keys). `clients.ts`:
`getClient` → `plan`, `usage { people, modulesOn, knows }`; `PATCH /api/clients/:id/plan` with history line.
Tests: signed only with accepts; payload for an older body unchanged; validation; history words; usage from the
newest check-in.

### Task 3: panel — Plan limits card
`components/PlanLimits.tsx` on the client page (canvas board): places chips + stepper, module rows with official
marks and switches (LUME's switch style ported to the panel), warnings for a module on now, Save + saved line, older
LUME note. Fleet's People column shows "n of m" when limited. Tests: chips/stepper bounds, Save sends exactly the
body, the warning text, older LUME.

### Task 4: LUME API — keep the plan
- `licence/plan.ts`: `planOf(view)`, `takenPlaces(db)`, `assertPlace(req)` (409 `PLAN_PLACES`), `assertModule(req,
  key)` (409 `PLAN_MODULE`), `applyPlan(pool, plan, notify)`: for each excluded module that is on, switch off
  (Sheets/Webhooks/Google Calendar: settings.integrations.<m>.enabled = false), audit `integration.disabled`
  (by "plan"), one admin notification; remembered in `licence_state.plan_applied jsonb` so it runs once per change
  (migration 0067).
- Invites (`createInvite`) and restore (`setDisabled(false)`) call `assertPlace` inside their transaction (advisory
  lock).
- Module switches (`setSheetsEnabled`, webhooks, `setCalendarEnabled`, Calendly connect) call `assertModule`.
- Calendly receive: excluded → 200 and ignored.
- Keeper: after a good check, `applyPlan` when the plan changed; health `modulesOn`.
- `LicenceForPerson.plan`: `{ places, taken, modules }` for people who manage settings; `null` otherwise.
Tests for each; the access matrix unchanged (no new routes).

### Task 5: LUME web
People: "4 of 5 places" and the over-limit line; the Invite sheet's up-front message and disabled Send.
Integrations: "Not in this LUME's plan" pill, switch disabled, Calendly Connect hidden. Tests.

### Task 6: e2e
Licence: the Plan limits card saves and the history says so. Web: the fake licence server signs `plan { places: N
}`; Invite shows the message and Send is disabled; an excluded module's card says so; screenshots reviewed.

### Task 7: deploy and record
Gate; licence server 0.5.0 (migration 0007; backup; rollback `pre-0007`); runbook; summary
`docs/control-2026-10-17.md`; push; CI.
