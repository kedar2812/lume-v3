# WhatsApp replies, part 1 (W1): connect a number, replies on the lead — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A business connects its existing WhatsApp Business app number(s) to LUME (coexistence), and every reply a lead sends, and every message sent from the phone, appears on that lead in LUME by itself; strangers wait in "Not a lead yet".

**Architecture:** Meta talks only to the connect relay (connect.lumecrm.in), which holds the Meta app secret. At connect,
the relay runs Embedded Signup, exchanges the code for the client's business token, subscribes that client's WhatsApp
account with its own callback address at the relay (`/wa/in/<instanceId>`), and hands the token back sealed to the
client's LUME, as Google's hand-back does. Meta's deliveries reach the relay, which checks Meta's signature, stores
nothing, and forwards the raw body to that instance's `/whatsapp/in`, signed with the instance's token. The client's LUME
stores each event once, then a queue matches it to a lead and writes it as an activity.

**Tech Stack:** Fastify + Drizzle + Postgres RLS, pg-boss, Next.js, zod 4, Vitest, Playwright; Meta WhatsApp Cloud API
(Graph) behind a fake in every test.

**Spec:** `docs/superpowers/specs/2026-10-18-whatsapp-replies-ai-design.md` — §3 (connection, Decision 1: through the
relay), §4.1 (matching), §4.2 (lead drawer thread, notifications), §6.3 (privacy). W2 (reply meaning, stop →
do-not-contact, the Who replied board, Today's Replies tile) and W3 (reply box §3.4, files and media templates §4.3) are
separate plans that build on this one.

## Global Constraints

- Owner (2026-10-18): "keep the ui super simple, follow the industry standard ui design specifics so that everything is predictable and accessible for the user"; "lets assume all scenarios while building". Build without waiting for permission; canvas before UI; owner reviews at the end.
- Optional module: off by default; needs the plan's `whatsapp` module (`assertModule(req, "whatsapp")`) and the relay configured (`GOOGLE_OAUTH_RELAY_URL/TOKEN`, the one relay connection). The app works with it off.
- Lead data leaves the client's server only to integrations that client enabled. The relay keeps nothing: message text passes through in memory only.
- The Meta app secret lives only on the relay. A client's business token lives only on that client's server, encrypted with the keyring (`keyring.encrypt(token, "whatsapp-number:<id>")`), never in logs, exports or health check-ins.
- Unknown numbers never become leads by themselves; "Not a lead yet" keeps them 14 days, then deletes them. AI never reads them (W2).
- History sync keeps only chats whose number matches a lead; the rest are dropped on arrival.
- Media: downloaded with the client's token to the client's server (Meta's links expire); at most 25 MB a file.
- Activities: `whatsapp_received` and `whatsapp_sent` (payload `{ text, wamid, numberId, media? }`), on the matched lead, following lead visibility.
- No client names in code; copy speaks as "LUME"; dates month first; no em dashes in UI copy.
- Graph API version comes from config (`META_GRAPH_VERSION`, default `v23.0`); every Meta URL is overridable for the fake.

## Review Focus

1. Meta delivers the same message twice (it retries until it gets a 200) → one activity, one notification (dedup on `wamid`, kind).
2. Two leads share the sender's number → the reply lands on one lead only: one the number's owner can see, most recently active first; never on both.
3. The instance is down when Meta delivers → the relay answers Meta with a non-2xx so Meta retries; a replayed forward (same signature) is refused after the first.
4. The client's token stops working (revoked, the number disconnected in the app) → the number shows "Reconnect", texts still arrive (they need no token), media waits and says why.
5. History arrives after live messages, and overlaps them → no duplicates, the thread stays in time order.

Each has its test in the owning task (Tasks 1, 2, 5, 6, 7).
